## SYSTEMIC ROOT CAUSES

Most of the 30 confirmed high findings are not independent — they cluster into seven recurring root causes. Fixing each root cause once resolves all the findings it covers. Tackle in roughly this order.

### (A) Streaming async messages are delivered only to the active screen

**Covers:** C0 (update stream stranded on tab-click), C1 (manage install result leaked on tab-click), C9 (leaving Manage mid-install strands `manageInstalling`), C15 (Ctrl+C during install doesn't stop the subprocess), and the medium C10 (post-wizard cache never invalidated).

**Root cause:** `App.Update` only special-cases `uiTickMsg`/`installCacheDoneMsg` globally; every other message is delegated to `sm.current` alone (`screen_manager.go:175`). The streaming pattern (`updateStreamMsg`, `manageInstallWithLogsMsg`, `manageInstallDoneMsg`, `installEventMsg`) re-arms / finalizes itself only while its originating screen stays active. Navigating away (esp. via the **mouse** tab-bar handlers, which — unlike the keyboard handlers — lack any `running` guard) drops the in-flight message, which permanently wedges state (`updateRunning`/`manageInstalling` never reset), drops the install/update result, leaks the worker + `streamPipe` goroutines, and orphans the (often sudo) brew/apt/pacman subprocess because nobody ever calls `StreamingCmd.Cancel()`.

**Systemic fix:** Handle the streaming/terminal async messages (`updateStreamMsg`, `manageInstallWithLogsMsg`, `manageInstallDoneMsg`, `manageStartInstallMsg`, `manageSudoRequiredMsg`, `installEventMsg`) **globally in `App.Update` before delegating**, exactly as `installCacheDoneMsg` already is — so the re-arm/finalize/cache-refresh chain survives navigation. Additionally retain the `*runner.StreamingCmd` (or a `context.CancelFunc`) on `App` so Ctrl+C and navigate-away can `Cancel()` and tear down the subprocess + goroutines deterministically. As a minimal stopgap, mirror the keyboard `running` guard in the mouse handlers (`screen_update.go` / `screen_manage.go`).

### (B) Config write-back is dead — edited settings never regenerate dotfiles

**Covers:** C12 (Manage dual-pane is a dead write-back), C26 (~80 Manage fields persist to JSON no generator reads), C27 (`dotfiles config <tool>` edits discarded on exit), C28 (two divergent tool→screen maps; CLI advertises broken tools), and the medium C13 (ManageConfig vs DeepDiveConfig divergence).

**Root cause:** The `WriteXConfig` generators (ghostty/tmux/zsh/neovim/git/yazi/fzf/lazygit/btop/glow/...) are invoked **only** from `installation.go`, reading `deepDiveConfig`. Three parallel config representations exist with no single source of truth and no enforced mapping: `config.*Config` JSON, `ui.deepDiveConfig` (never persisted), and `ui.ManageConfig` (persisted to `manage.json` but never read by any generator). So the Manage editor and standalone `dotfiles config <tool>` both report "Saved ✓" while writing nothing to the actual dotfiles. Field names and value vocabularies also diverge between models (e.g. tmux prefix `C-a` vs `ctrl-a`).

**Systemic fix:** Collapse to **one canonical config representation per tool** (the `tools.*Config` generator input is the natural source of truth). Have both the installer and the Manage screen edit that same type, with a single `apply` function that calls the `WriteXConfig` generators. Wire `saveManageConfigCmd` and the standalone `config <tool>` back()-path to that apply step. Reconcile the divergent option vocabularies. Unify the two tool→screen maps (`GetToolConfigScreen` vs `toolConfigScreens`) and fix the CLI help/error strings. Add a round-trip test proving a UI edit changes the generated config file.

### (C) "Reports success but did nothing" (silent failure in safety-critical paths)

**Covers:** C3 (TUI restore discards skipped files; full-fail reports success), C5 (pre-install auto-backup claims success on empty/failed backup), C6 (multi-package tool marked installed when only `pkgs[0]` present), C14 (install short-circuits and applies ZERO configs when all tools already installed), and the medium C4 (backup creation success on zero files / manifest-write failure), plus bash C22 below.

**Root cause:** Error-swallowing `continue` loops, dropped `WriteFile` errors, success counts that aren't checked, and `IsInstalled` checking only `pkgs[0]` while `Install` installs all packages. The highest-stakes case (C5) prints "✓ Auto-backup created" immediately before overwriting `~/.zshrc`/`~/.gitconfig`/etc., removing the user's only rollback path while affirmatively claiming it exists.

**Systemic fix:** In every backup/restore/install reporting path, track a real success count and propagate write errors. Don't claim success unless ≥1 file was captured and the manifest persisted; surface skipped files (mirror the CLI, which does it correctly). Make `IsInstalled` (and the `cache.go` batch check at `cache.go:83/164`) verify **all** packages, not just `pkgs[0]`. Decouple config application from package selection so re-running the wizard re-applies configs even when nothing new installs (C14).

### (D) themeReturn / wizard-step-reused-as-standalone navigation is incomplete

**Covers:** C7 (`dotfiles theme` no-arg drags user into installer wizard, never persists), C8 (stale `themeReturn` from main-menu Theme derails a later deep-dive install).

**Root cause:** "Standalone theme picker" is inferred implicitly from `themeReturn == ScreenMainMenu` rather than being an explicit mode. `themeReturn` is persistent global mutable App state with only one entry point (quick-setup) defensively resetting it. The CLI path and the deep-dive "Continue to Installation" path both leave a stale/default value, so the picker can't tell standalone from wizard step 2 — Enter either escapes into NavPicker/FileTree or bounces to MainMenu mid-install, discarding selections without persisting.

**Systemic fix:** Replace the implicit `themeReturn` sentinel with an **explicit `themeStandalone` flag**, set it at every ThemePicker entry (CLI, main-menu, both wizard paths), and branch Enter/Esc on it. Ensure `persistTheme()` runs on Enter in the standalone path. Add regression coverage for the standalone-CLI and deep-dive-continue entries (currently untested).

### (E) Systematic mouse hit-detection offsets

**Covers (all medium):** C17 (~12 field-config screens: 1 row/field assumed, 3 drawn + wrong vertical anchor), C18 (backups list off-by-one), C19 (users settings-pane ignores description line), C20 (theme picker container height underestimated, X-bounds hardcoded).

**Root cause:** Click→item mapping is computed from hand-maintained constants that don't match the real rendered layout (border/padding rows, multi-row fields, variable-height selected rows, HelpStyle padding). Wheel-scroll works because it ignores geometry; clicks systematically select the wrong item or none.

**Systemic fix:** Stop hand-deriving Y offsets. Have each View record per-item `(startY, height)` into a slice the mouse handler resolves against, and add X-bounds checks against the centered box. As a batch, recompute the constants to include title/border/padding/HelpStyle and the true rows-per-field. The field-config base (`configFieldNav`, C17) fixes ~12 screens at once.

### (F) Option/value mismatch — UI offers a value the generator can't handle (ghostty-class bug)

**Covers:** C25 (neovim 'nvchad' preset silently degrades to a minimal hand-rolled config while the UI prints "Neovim configured (nvchad)").

**Root cause:** Same structural defect as the already-fixed ghostty alt/TabBindings bug: a config screen offers an option value (`nvchad`) that the generator's switch doesn't match, so it falls through to a default — with no error, and an affirmative success message that lies about what was installed. `neovimConfigRepos` and the `WriteNeovimConfig` switch only know kickstart/lazyvim.

**Systemic fix:** Either add nvchad to `neovimConfigRepos` + the switch, or remove it from the screen until supported. Long-term, make presets typed enums (`type NeovimPreset string` with a const set) and add a table-driven test asserting **every option the screen offers** produces a config reflecting that option — generalize the existing TabBindings regression test to all option/value pairs to prevent the whole bug class.

### (G) Embedded bash `dotfiles` CLI bugs (two copies of logic drifted)

**Covers:** C22 (CRITICAL — installed `dotfiles restore` restores nothing: undefined `is_safe_restore_path` in the embedded CLI heredoc), C23 (embedded CLI can't theme catppuccin-frappe/macchiato, silently renders Mocha), and the medium C24 (`--theme` with no value aborts under `set -u`).

**Root cause:** `bin/dotfiles-setup` contains the outer setup script **and** an embedded `dotfiles` management CLI heredoc that duplicates functions (`is_safe_restore_path`, `load_theme_colors`). The copies have drifted: the embedded restore calls a function that was never pasted into the heredoc (→ 127 not-found → every file skipped → restore is a total no-op), and the embedded `load_theme_colors` is missing two themes that its own `SUPPORTED_THEMES` advertises.

**Systemic fix:** Paste the missing `is_safe_restore_path` body into the `DOTFILES_CLI_EOF` heredoc (fixes C22). Add the frappe/macchiato cases to the embedded `load_theme_colors` and make the `*)` default error instead of silently substituting Mocha (C23). Guard `--theme`'s `$2` with `${2:-}` (C24). Long-term, generate the embedded CLI's duplicated tables/functions from a single source so the two copies cannot drift. Add a smoke test running the generated `~/.local/bin/dotfiles restore` against a fixture.

## CONFIRMED CRITICAL / HIGH (30)

Ordered roughly by blast radius. `C#` = finding index for cross-reference from the root-cause section.

### C0. Live update stream is permanently stranded (goroutine + subprocess leak, wedged UI) if the user mouse-clicks another tab while an update is running

- **Severity:** HIGH | **Dimension:** concurrency
- **Location:** `internal/ui/screen_update.go` : 120-131, 291-307
- **Problem:** The streaming update uses the channel + re-armed listen-Cmd pattern: each updateStreamMsg appends one line and RE-ISSUES listenUpdateStreamCmd (line 131) to pull the next event. This re-arm chain only survives while the Update screen is the ScreenManager's active screen, because updateStreamMsg is handled ONLY in updateScreen.Update (no global fallback in App.Update, unlike the fixed uiTickMsg/installCacheDoneMsg at app.go:770/784).

The keyboard handler blocks tab navigation while updateRunning (handleKey line 196 guard precedes tabNavigationTarget at line 202), BUT the MOUSE handler has no such guard: handleMouse (291-307) calls navigateTab on any tab-bar click regardless of a.updateRunning. Manage, Users, Hotkeys, Update, Backups are all tabs in the same RenderTabBar (styles.go:758-766), so a single click switches the active screen mid-stream.

Consequence chain, traced: (1) Bubble Tea delivers the in-flight updateStreamMsg to whatever handler is active at delivery time; after the tab switch that is e.g. manageScreen.Update, which does not handle updateStreamMsg, so it is dropped and listenUpdateStreamCmd is never re-issued. (2) The worker goroutine (installation.go:671-686 / 710-717) keeps writing lines to the buffered channel a.updateStream (cap 64, installation.go:668/707). Once 64 lines accumulate unread, `stream <- updateStreamMsg{line: line}` blocks forever -> the worker goroutine and the runner's two streamPipe goroutines + the subprocess (cmd.Wait never reached) all leak. Nothing ever calls StreamingCmd.Cancel() (the *StreamingCmd is never even retained on App; only the channel is), so the brew/apt/pacman child process is orphaned. (3) a.updateRunning is never reset (finishUpdate only runs on the dropped done event), so returning to the Update tab shows a frozen 'UPDATING' log panel; updateScreen.Init re-arms only checkUpdatesCmd, never listenUpdateStreamCmd (lines 60-70); and handleKey blocks r/esc/everything behind the updateRunning guard (line 196). The screen is permanently wedged; only q/ctrl+c (full quit) escapes.
- **Fix:** Mirror the keyboard guard in the mouse path: in updateScreen.handleMouse, return early when a.updateRunning before calling navigateTab (same as handleKey line 196). More robustly, make the streaming async messages resilient to screen switches: either (a) handle updateStreamMsg/manageInstallWithLogsMsg/installEventMsg globally in App.Update (like uiTickMsg/installCacheDoneMsg) so the re-arm/finalize chain survives navigation, or (b) retain the *runner.StreamingCmd on App and call Cancel() + reset updateRunning/updateStream when leaving the Update screen so the subprocess and goroutines are torn down deterministically.

### C1. Manage tool-install can leak its result and permanently stick manageInstalling=true when the user mouse-clicks another tab mid-install

- **Severity:** HIGH | **Dimension:** concurrency
- **Location:** `internal/ui/screen_manage.go` : 148-169, 521-544
- **Problem:** streamingInstallToolCmd (installation.go:581-621) runs the package install inside a tea.Cmd closure and returns a single terminal manageInstallWithLogsMsg. That message is handled ONLY in manageScreen.Update (line 148) with no global fallback in App.Update. The manage mouse handler (handleMouse, 521-544) routes a tab-bar click to navigateTab with NO manageInstalling guard (the keyboard 'i' path guards via line 360, but tab switching does not). Manage/Users/Hotkeys/Update/Backups are sibling tabs (styles.go:758-766), so a click switches the active screen while the install Cmd is still running.

Traced consequence: when manageInstallWithLogsMsg finally arrives, if the active screen is no longer Manage it is dropped. a.manageInstalling stays true (only reset at screen_manage.go:113/150, which never run) and the install-status cache refresh (startInstallCacheLoad re-issue at 165) never fires. On returning to Manage, Init() (lines 67-73) does NOT reset manageInstalling, and handleKey 'i' (line 360) early-returns whenever manageInstalling is true -> the user can never start another install from the Manage screen for the rest of the session, and the just-installed tool is not reflected. (Note: the underlying subprocess itself does complete here, unlike the Update-stream case, because the collect-then-message worker drains cmd.Output fully inside the Cmd goroutine; the leak is the stuck flag + dropped result, not a blocked goroutine.)
- **Fix:** Add an `if a.manageInstalling { return nil }` guard at the top of the tab-click branch in manageScreen.handleMouse (parallel to the keyboard 'i' guard), and/or reset manageInstalling=false in manageScreen.Init() on re-entry. The durable fix is to handle manageInstallWithLogsMsg globally in App.Update so the terminal result and cache-refresh always apply regardless of which screen is active when the Cmd returns.

### C2. usersScreen.View panics (negative strings.Repeat count) at small terminal heights/widths

- **Severity:** HIGH | **Dimension:** panics
- **Location:** `internal/ui/screen_users.go` : 618-653, 687, 765
- **Problem:** usersScreen.View computes layout dimensions by raw subtraction/division with no lower clamp, then feeds the results into strings.Repeat, which panics on a negative count.

Trace:
- Line 620-625 guard: it only short-circuits to "Loading..." when BOTH a.width==0 AND a.height==0 (the inner branch additionally requires width<=0||height<=0). If a.width and a.height are already set to small POSITIVE values (e.g. 2x2 or 80x2 after a resize), the guard is entirely skipped and execution falls through.
- Line 633: contentHeight := a.height - 4. For a.height in {1,2,3} this is negative.
- Line 644: lipgloss...Render(strings.Repeat("│\n", contentHeight)) -> strings.Repeat with a negative count -> panic: "strings: negative Repeat count".
- Independently, line 631-632: leftWidth := a.width/3; rightWidth := a.width - leftWidth - 3. For a.width<=2, rightWidth is negative; renderUsersSettingsPane line 765 calls strings.Repeat("─", width) with that negative width -> same panic.

Reachability: a.width/a.height are assigned verbatim from tea.WindowSizeMsg in App.Update (internal/ui/app.go:760-762) with no minimum clamp, and ScreenManager.View (screen_manager.go:195) passes ctx.Width/ctx.Height straight to the handler. Terminals legitimately emit tiny sizes (1x1, 2x2) transiently while a tmux pane or window is dragged very small, so the crash is user-reachable.

Proof: I drove the Factory-created handler for ALL 33 migrated screens through View() at dims {0x0,1x1,2x2,3x3,1x24,80x1,80x2,80x3,5x5,4x4}. ScreenUsers (id 23) was the ONLY screen that panicked, and it panicked at 1x1, 2x2, 3x3, 80x1, 80x2, 80x3 with exactly "strings: negative Repeat count". The 80x2 case (width fine, height tiny) isolates the line 644 height path; the 2x2 case also exercises the line 765 width path. Every other screen (Manage, Update, Hotkeys, Backups, config screens, animation, progress, etc.) survived all tiny dimensions because they consistently use maxInt(...)/min(...) clamps and truncateVisible/truncatePlain both guard width<=0.
- **Fix:** Clamp the derived dimensions before any strings.Repeat. Simplest: at the top of usersScreen.View, after the existing guard, add a hard floor, e.g. treat a.width<MIN or a.height<MIN as the loading/too-small state, OR clamp contentHeight := maxInt(0, a.height-4), leftWidth := maxInt(0, a.width/3), rightWidth := maxInt(0, a.width-leftWidth-3), and guard the separator with `if contentHeight > 0`. Mirror the pattern other screens already use (maxInt/min). Also fix the guard at line 620-625 so it triggers on small positive dims, not only exact-zero, to match how Manage/Update screens fall back.

### C3. TUI backup restore silently discards skipped files; a fully-failed restore reports success

- **Severity:** HIGH | **Dimension:** error-handling
- **Location:** `internal/ui/app.go` : 537-551
- **Problem:** restoreBackupCmd calls backup.Restore, which returns a RestoreResult whose Skipped map records every file that could NOT be restored (path-traversal rejection, write-through-symlink refusal, read error, mkdir error - see internal/backup/backup.go:203-229). The TUI path only reads result.Count() (the number of SUCCESSFUL files) and constructs backupRestoreDoneMsg{count: result.Count(), err: nil}. result.Skipped is thrown away entirely. The backups screen then renders 'Restored N files from X' with a green success style (screen_backups.go:90-93, 306-308). Consequence: a restore where every file is skipped reports 'Restored 0 files from X' as SUCCESS with no error and no hint that anything was skipped. The user believes their dotfiles were restored when nothing was written. The CLI path does this correctly - cmd/dotfiles/main.go:638-642 iterates result.Skipped and prints each 'skipped: reason' line - so the two surfaces diverge and the TUI is strictly worse. This is a real 'failure looks like success' in a data-restore path.
- **Fix:** In restoreBackupCmd, inspect len(result.Skipped) and either fold it into the message ('Restored %d files (%d skipped)') or attach the skipped details to backupRestoreDoneMsg so the Backups screen can surface them. At minimum show a non-success style when Skipped is non-empty, mirroring the CLI's behavior so the two restore paths cannot diverge.

### C4. Backup creation reports success even when zero files were backed up or the manifest write fails

- **Severity:** MEDIUM | **Dimension:** error-handling
- **Location:** `internal/ui/app.go` : 586-621
- **Problem:** createBackupCmd loops over a fixed filesToBackup list and silently `continue`s on every os.Stat, os.ReadFile, or os.WriteFile error (lines 590-605). It then writes the manifest with the error discarded (`_ = os.WriteFile(manifestPath, ...)` line 615) and unconditionally returns backupCreateDoneMsg{name: timestamp, err: nil}. Two distinct silent-failure modes result: (1) If none of the source files exist or all writes fail (e.g. disk full, permission denied on the backup dir contents), an EMPTY backup directory is created and the screen shows 'Created backup: <timestamp>' in green (screen_backups.go:117-119) - the user believes they have a safety copy that contains nothing. (2) If the per-file copies succeed but the manifest write fails, the backup silently degrades to a manifest-less 'legacy' backup that restores via lossy underscore decoding (backup.go:184-200), which mis-maps any path component that legitimately contained an underscore. Neither failure surfaces.
- **Fix:** Track a real success count and propagate the manifest write error: if len(backedUp)==0 return backupCreateDoneMsg{err: fmt.Errorf("no files were backed up")}; check the manifest WriteFile error and return it instead of discarding it. Optionally report how many of the candidate files were actually captured.

### C5. Pre-install auto-backup reports '✓ Auto-backup created' even when it backed up nothing

- **Severity:** HIGH | **Dimension:** error-handling
- **Location:** `internal/ui/installation.go` : 126-133
- **Problem:** Before an install overwrites the user's configs, the worker calls autoBackupIfEnabled() (app.go:687-754). That function uses the same swallow-on-error loop as createBackupCmd: every os.Stat/os.ReadFile/os.WriteFile failure is `continue`d (app.go:723-738) and the manifest WriteFile error is dropped entirely (app.go:748, not even assigned to _, which errcheck would flag). It returns nil as long as MkdirAll on the backup dir succeeded, regardless of whether ANY file was captured. The install worker treats a nil return as success and emits '✓ Auto-backup created before installation' (installation.go:131), then proceeds to overwrite ~/.zshrc, ~/.gitconfig, ~/.tmux.conf, etc. Consequence: the safety-net backup that exists specifically to let the user recover from a bad install can be silently empty while the UI affirmatively claims a backup was made. This is the highest-stakes 'failure looks like success' because it removes the user's only rollback path right before destructive writes.
- **Fix:** Make autoBackupIfEnabled return an error (or count) when zero files were captured or the manifest write fails, and have the install worker surface that as a real warning ('⚠ Auto-backup captured 0 files') instead of the unconditional success line. Do not claim a backup was created unless at least one file was written and the manifest persisted.

### C6. Multi-package tools report installed when only the first package is present, hiding partial install failures

- **Severity:** HIGH | **Dimension:** error-handling
- **Location:** `internal/tools/tool.go` : 129-150
- **Problem:** BaseTool.Install installs ALL platform packages via mgr.Install(pkgs...) (line 149), but BaseTool.IsInstalled only checks pkgs[0] (line 141: `return mgr.IsInstalled(pkgs[0])`). Several tools define multiple Linux packages: claude-code -> {nodejs, npm} (claude_code.go:33-34), zsh -> {zsh, zsh-autosuggestions, zsh-syntax-highlighting, zsh-completions} (zsh.go:40-41), yazi -> 10 packages on Arch (yazi.go:36). If a secondary package fails to install (npm, zsh-completions, ffmpegthumbnailer, etc.) while pkgs[0] succeeds, IsInstalled returns true. Two failure-looks-like-success paths follow: (a) the install worker's 'Skip if already installed' guard (installation.go:163-167) marks the tool ✓ and counts it toward 'All N tools installed successfully'; (b) the Manage screen's post-install cache refresh (screen_manage.go:160-166) shows 'Installed successfully ✓'. Worse, collectSelectedTools filters out any tool where manageInstalled[id] is true (installation.go:546-563, `!a.manageInstalled[id]`), so a partially-installed multi-package tool is permanently excluded from re-install - the missing secondary packages can never be repaired through the UI.
- **Fix:** Have IsInstalled verify ALL packages for the platform (loop over pkgs and require mgr.IsInstalled(p) for each), not just pkgs[0]. This makes partial installs visible to both the install-skip guard and the Manage cache, and lets a re-run repair the missing packages.

### C7. `dotfiles theme` (no-arg CLI) launches the theme picker as a wizard step: Enter drags the user into the installer's nav-style screen and never persists the theme; Esc dumps into the install welcome

- **Severity:** HIGH | **Dimension:** navigation

SetStartScreen never touches a.themeReturn, so it keeps its constructor default ScreenWelcome (app.go:338). The migrated theme picker treats `themeReturn == ScreenMainMenu` as the ONLY 'standalone' entry (screen_themepicker.go:64,72). With themeReturn==ScreenWelcome, pressing Enter falls through to `return s, NavigateTo(ScreenNavPicker)` (line 70) -- pushing the user into the install wizard's navigation-style step (which then chains NavPicker->FileTree->Progress). Esc falls through to NavigateTo(ScreenWelcome) (line 78), landing on the installer welcome screen. Net result: the documented `dotfiles theme` standalone picker cannot apply-and-exit a theme; it either escapes into the installer wizard or silently discards the selection. - **Fix:** Make 'standalone theme picker' an explicit mode rather than inferring it from themeReturn==ScreenMainMenu. Either have SetStartScreen(ScreenThemePicker) set a.themeReturn to a standalone sentinel (and persist+quit on Enter, quit on Esc for the CLI case), or add an explicit a.themeStandalone bool set by SetStartScreen and the main-menu entry, and branch on it in screen_themepicker.go Enter/Esc. Ensure persistTheme() runs on Enter in the standalone path.

### C8. Stale `themeReturn` from main-menu 'Theme' leaks into a later install wizard run: the deep-dive 'Continue to Installation' theme step then persists+exits to MainMenu instead of advancing, derailing installation

- **Severity:** HIGH | **Dimension:** navigation
- **Location:** `internal/ui/screen_mainmenu.go, internal/ui/screen_deepdivemenu.go, internal/ui/screen_themepicker.go` : screen_mainmenu.go:75-78; screen_deepdivemenu.go:54-60; screen_themepicker.go:63-78
- **Problem:** a.themeReturn is a persistent App field. Selecting 'Theme' from the main menu sets a.themeReturn = ScreenMainMenu (screen_mainmenu.go:78) and it is NEVER reset on exit from the picker (the picker only reads it; nothing clears it). The install wizard's quick-setup path defensively resets it (screen_welcome.go:52 sets themeReturn = ScreenWelcome before NavigateTo(ScreenThemePicker)), but the DEEP-DIVE path does not: deepDiveMenuScreen.selectItem's 'Continue to Installation' branch does `return NavigateTo(ScreenThemePicker)` with no themeReturn reset (screen_deepdivemenu.go:57-60). Trace: MainMenu -> 'Theme' (themeReturn=ScreenMainMenu) -> esc back to MainMenu -> 'Install' -> choose Deep Dive -> configure tools -> 'Continue to Installation' -> ThemePicker. Now themeReturn is still ScreenMainMenu, so Enter hits the standalone branch: persistTheme() + NavigateTo(ScreenMainMenu) (screen_themepicker.go:64-68) -- the install wizard is abandoned (NavPicker/FileTree/Progress never reached) and the user is silently bounced to the main menu mid-install. Esc likewise reverts the theme and returns to MainMenu (lines 72-76), discarding all deep-dive selections. This is the same class as the original theme-picker-from-main-menu bug but on the reverse path, left unfixed because themeReturn is global mutable state with only one entry point resetting it.
- **Fix:** Set the return context at every ThemePicker entry, not just quick-setup. In deepDiveMenuScreen.selectItem's Continue branch set a.themeReturn = ScreenWelcome (wizard semantics) before NavigateTo(ScreenThemePicker). ### C9. Leaving Manage screen mid-install permanently strands manageInstalling=true; terminal install message is dropped by the now-active screen

- **Severity:** HIGH | **Dimension:** state-mgmt
