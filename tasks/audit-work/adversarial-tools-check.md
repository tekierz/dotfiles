## New release findings

### N01 — Critical — The advertised auto-backup does not cover most destructive writers and failure does not stop install

`internal/ui/app.go:735-745` backs up only `.zshrc`, `.tmux.conf`, Neovim's
`init.lua`, Ghostty's XDG file, `yazi.toml`, and `.gitconfig`. The install worker then
whole-file replaces Yazi's `keymap.toml` and `theme.toml`, fzf, LazyGit, btop (plus a
theme file), and Glow (`internal/ui/installation.go:419-466`) without capturing them.
It also mutates Claude's real `~/.claude.json`, which is absent from the list.

Worse, `runInstallWorker` treats `autoBackupIfEnabled()` failure as a warning and
continues (`installation.go:201-210`). Combined with the core-lane finding that a
partially captured backup can silently omit individual files, the UI can print that a
rollback point exists and then perform the F01/F02 replacements without a usable
rollback for every affected file. README's “All existing configs are backed up” claim
is false.

**Release action:** destructive configuration phases must stop on backup failure by
default; derive the backup set from the exact write plan; verify every intended source
was captured; and back up immediately before Manage/theme writes too.

### N02 — High — Legacy generated Zsh migration deletes later user additions

The primary report called Zsh a safe managed-section exception. That is true for a
file already carrying both managed markers, but not for migration. If `.zshrc` starts
with `# Generated by dotfiles TUI`, `mergeZshManagedSection` returns only the new
managed block (`internal/tools/zsh.go:393-395`). Any aliases, exports, functions, or
comments the user appended to the old generated file are deleted on the first new
Save/Install. There is no immediate Manage backup.

**Release action:** parse/migrate only the known old generated region, preserve
unrecognized tail content, show a diff, and cover this exact appended-customization
case with a test.

### N03 — High — Manage theme changes reset settings that the installer models but Manage does not store

`changedManageTools` intentionally returns every generator on a theme change
(`internal/ui/manage_save_scope.go:117-132`). `manageConfigToDeepDive` begins from
`NewDeepDiveConfig()` defaults, then overlays only fields present in `ManageConfig`
(`config_apply.go:390-522`). Therefore a theme Save silently resets modeled-but-omitted
values before rewriting files, including:

- Ghostty tab bindings;
- tmux split bindings;
- Zsh prompt style, plugin selection, and aliases;
- Neovim LSP/plugin selections;
- Git aliases and side-by-side choice;
- Yazi keymap and preview mode.

It also applies all generators without checking whether the primary tool is installed,
so a theme Save can create new default config files for absent tools. This is separate
from F01's loss of unknown upstream keys: even settings this repository already models
are reset because its wizard and Manage state models are not round-trippable.

**Release action:** one imported canonical per-tool model; change only palette-owned
keys on a theme operation; never synthesize missing fields from defaults during
adoption.

### N04 — Medium — Current Go Yazi keymap emits a nonexistent selection action and mislabels Emacs navigation

`GenerateYaziKeymap` writes `run = "select --state=none"` for Space
(`internal/tools/yazi.go:203`). Current Yazi documents the manager action as `toggle`,
with optional `--state=on|off`; it documents no manager `select` action or
`--state=none`. The generated primary selection key is therefore broken on current
Yazi. The config screen also labels Emacs mode “Emacs (arrows)” while the generated
bindings are Ctrl-p/n/b/f (`internal/ui/screen_config_yazi.go:65-68`,
`internal/tools/yazi.go:179-186`). See the official current
[Yazi keymap reference](https://yazi-rs.github.io/docs/configuration/keymap/).

### N05 — High — The recommended Homebrew command is demonstrably tied to the older build

The installed tap is available at Homebrew's real tap checkout even though it was not
at the primary report's expected sibling path. Its `Formula/dotfiles.rb` installs tag
`v2.0.1`; `/opt/homebrew/bin/dotfiles` links to Cellar `2.0.1` and reports 2.0.1.
The fresh source binary reports `7ddcb99`. The formula caveat also advertises the
invalid `dotfiles theme --list`; both the installed and current source binaries exit 1
for that syntax.

This directly answers the original local-build question: **yes, the bare `dotfiles`
command currently resolves to the older Homebrew build**. It does not explain planned
AI tools, because those are absent from current source too, but it absolutely makes
source-vs-local behavior drift harder to diagnose.

**Release action:** do not advertise `brew install dotfiles` as current until the tap
is released from the intended tag and clean-machine install/upgrade/rollback tests pass.

## Planned AI tools: current authoritative corrections

All six remain absent from current code; they exist only in `tasks/new-tools-spec.md`.
That is why even the fresh `7ddcb99` source build lacks them.

- Current official [OpenAI Codex CLI docs](https://developers.openai.com/codex/cli/)
  prefer the standalone macOS/Linux installer, while npm and Homebrew remain tabs.
  [Codex authentication](https://developers.openai.com/codex/auth/) supports ChatGPT
  or API-key sign-in for local work and applies different workspace/data policies.
- [OpenCode's current docs](https://opencode.ai/docs/) still support curl/npm/Bun and
  Homebrew, but recommend their tap for faster updates; current Arch also has an
  official `pacman -S opencode` route.
- [Pi's current docs](https://pi.dev/docs/latest) still confirm the npm package,
  `--ignore-scripts`, curl installer, and `pi` binary. Its official
  [security page](https://pi.dev/docs/latest/security) explicitly says there is no
  built-in sandbox and extensions run with the user's permissions. Default-on is
  inappropriate for family or mock-enterprise rollout.
- The official [T3 Code cask](https://formulae.brew.sh/cask/t3-code) is now 0.0.28,
  not the spec's 0.0.27, and requires macOS 12+. The sample constructor still omits
  the `platformFilter` field that its prose requires.

Recommended implementation order remains: safe ownership/import/status schema first;
then add agents as explicit opt-in integrations with install source/version/digest,
auth and egress disclosure, permission/sandbox posture, and an enterprise allowlist.

## Repo and rename conclusions

The **keep this repository** recommendation is sustained. The unsafe parts are
replaceable seams, while the registry, package abstraction, TUI, tests, backup format,
and history are reusable. Freeze/remove the legacy product and refactor in place. A
new repository makes sense only for a genuinely separate centrally managed fleet
product (remote policy/execution, tenant auth, audit logs, MDM), not as cleanup.

Rename difficulty remains **8/10** for a safe product/distribution/data migration and
about **4/10** for display text only.

Correct counts at `7ddcb99`:

- Case-insensitive Git-blob scan: **123 tracked paths / 1,168 matches**.
- Filesystem scan following the `AGENTS.md -> CLAUDE.md` symlink: **124 paths / 1,195
  matches**; the extra path and 27 matches are the same target counted twice.
- Exact Go module/import string: **100 occurrences** (99 in Go, one in `go.mod`).
- High-impact command/config/repository/distribution strings: **90 tracked paths**.

The primary report's 118-file number is the case-sensitive, symlink-following view;
case-insensitive counts are the safer branding inventory. The migration sequence in
the primary report—display name first, binary alias, dual-read config roots, managed
marker compatibility, Homebrew transition, module path last—is sound.
