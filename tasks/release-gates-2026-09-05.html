Read a pass narrowly. A no-op package update proves its execution path, not a real version upgrade or rollback. An ownership-only tap fix preserves existing executables, but leaves the released product version unchanged.

The next useful decisions.

  1. Keep the passing evidence bound to its source

    Retain combined CI, hosted Homebrew logs and PTY records with their tested commits. The Homebrew markers and ten PTY assertions are recorded. These passes support review of draft PR #1; merging it remains an owner decision.

  2. Design a real version transition

    Choose immutable old/new artifact or package versions and an isolated fixture. Define successful upgrade, expected configuration/receipt changes, and rollback recovery before execution. The current no-op update and same-version Homebrew cycles do not satisfy this gate.

  3. Agree on supported platform coverage

    Decide which Arch, Raspberry Pi, npm/MCP and terminal scenarios must pass for the chosen release. Execute them in appropriate disposable or explicitly approved environments; keep unavailable hardware and credentials visible.

  4. Review the exact promotion candidate

    Only after required gates pass: review main promotion, the release version, protection policy and final artifact publication. A draft PR or generated archive is not release authorization.

Disposable automation next

Exact-version upgrade & rollback

Pin the before/after packages or kegs, capture current configuration and receipts, and prove both upgrade outcome and recovery. Include an interrupted or failed transition where the release contract requires it.

Dependency: selected versions and a reviewed disposable fixture. No older-keg fixture is claimed here.

Hardware / platform

Arch & Raspberry Pi

Exercise the relevant pacman/paru route and supported Pi environment. Check manager availability, installation health and terminal behavior on the actual platform.

Debian CI does not stand in for Arch or Pi hardware evidence.

Credentials / live integration

npm & MCP authentication

Test supported install phases, fresh confirmations and actual tool/server startup. Verify authentication with explicitly approved credentials and record the supported platform.

Version pins and recipe tests do not demonstrate a working authenticated service.

Owner observation

Terminal appearance & recovery

Review theme contrast, glyphs, navigation, resizing and mouse behavior in the owner's terminal. Confirm backup/restore expectations with a reviewed recovery fixture.

A PTY captures program behavior; it does not establish the appearance of every font or terminal.
